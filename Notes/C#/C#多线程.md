## C#多线程



### 什么是线程`Thread`？

- 线程Thread是操作系统中能够独立运行的最小单位，也是程序中能够并发执行的一段指令序列
- 线程Thread是**进程Process**的一部分，一个**进程Process**可以包含多个线程Thread，这些线程共享进程的资源
- **进程Process**有入口线程Thread，也可以创建更多的线程Thread



### 为什么要多线程？

- **提高响应性**：主线程保持UI响应，后台线程处理耗时操作
- **利用多核CPU**：并行计算提升性能（如图像处理、科学计算）。
- **异步操作**：同时处理多个I/O请求（如网络通信、数据库查询、批量重复任务希望同时进行）。



### 什么是线程池`ThreadPool`？

1. **线程池**是一种管理和复用线程的机制，用于减少线程创建/销毁的开销，提高多线程程序的性能和资源利用率。
2. **线程池**维护一组预先创建的**工作线程**，当有任务需要执行时，从池中分配空闲线程处理任务，任务完成后线程返回池中等待下一次分配（而非被销毁）。



### 为什么现在很少和线程池打交道？

为简化线程管理，C#提供了更高级的抽象：

- **`Task`（任务）：**基于线程池的轻量级并发模型（推荐首选）
- **`async/await` 异步编程：**避免阻塞线程，高效利用资源
- **`Thread`类： **仅在需要精细控制线程行为时使用



### 什么是线程不安全？

- **竞态条件**：多个线程对共享数据的操作顺序不确定，导致结果依赖于线程调度的随机性。
- **脏读**：线程读取到另一个线程未完成修改的中间状态数据。
- **死锁**：多个线程相互等待对方释放资源，导致程序永久阻塞。
- **内存可见性问题**：因CPU缓存优化，一个线程的修改对其他线程不可见。



### 线程不安全的常见场景

- **非原子操作**

  - 看似简单的操作（如 `i++`）实际包含“读-改-写”三步，可能被其他线程中断。

- **使用非线程安全的集合**

  - `List<T>`、`Dictionary<TKey, TValue>` 等在并发写时会崩溃或数据损坏。

  - **错误示例**：

    ```C#
    List<int> list = new List<int>();  
    Parallel.For(0, 1000, i => list.Add(i)); // 抛出异常或数据丢失  
    ```

- **未保护的共享状态**

  - 全局变量、静态字段、单例对象等未加锁访问。

- **组合操作的非原子性**

  - 即使单个方法是线程安全的，组合调用仍可能不安全：

    ```C#
    if (!dict.ContainsKey(key))  
        dict.Add(key, value); // 其他线程可能已插入  
    ```

    

### 什么是线程安全？

- **线程安全**：多个线程访问共享资源时，对共享资源的访问不会导致数据不一致或不可预期的结果。
- **同步机制**：用于协调和控制多个线程之间执行顺序和互斥访问共享资源；确保线程按照特定的顺序执行，避免竞态条件和数据不一致的问题。
- **原子操作**：在执行过程中不会被中断的操作。不可分割，要么完全执行，要么完全不执行，没有中间状态；在多线程环境下，原子操作能够保证数据的一致性和可靠性，避免出现竞态条件和数据竞争的问题。



> [!IMPORTANT]
>
> ### 常见实现线程安全的方式？
>
> - 线程
> - 线程池
> - 异步编程
> - 自带方法：`Parallel`----`For`、`Foreach`、`Invoke`
> - 自带方法：`PLINQ`----`AsParallel`、`AsSequential`、`AsOrdered`



## C#线程Thread

#### 线程的创建

1. 创建 Thread 实例，并传入 `ThreadStart` 委托。还可以配置线程，如是否为后台线程。
2. 调用 `Thread.Start` 方法，还可以传参。

#### 线程的终止

- 调用 `Thread.Join` 方法，等待线程的结束
- 调用 `Thread.Interrupt` 方法，中断线程的执行
  - 使用`try catch`,会在相应线程中抛出`ThreadinterruptedException`
  - 如果线程中包含一个 `while(true)` 循环，调用 `Thread.Interrupt` 方法会没办法得到回应，因为它一直在忙，没办法回应你。为了解决这个问题，要保证线程中包含等待方法，如`I0`操作，`Thread.Sleep`等。

- 不能用`Abort`?（过时的方法）
  - 使用 Abort 方法来强制终止线程可能导致一些严重的问题，包括资源泄漏和不可预测的行为
  - 较新版本的 .NET 中如果使用这个方法，会报`PlatformNotSupportedException`
  - 推荐使用 `Thread.Interrupt` 或`CancellationToken`

#### 线程的挂起与恢复

1. `Thread.Suspend` 以及 `Thread.Resume`
2. 较新版本的 .NET 中，这两个方法已经被标记为`Obsolete`，且调用会报错
3. 推荐使用锁、信号量等方式实现这一逻辑





## 多线程 不等于 异步

1. 异步并不意味着多线程，单线程也可以异步
2. 异步默认借助线程池
3. 多线程经常阻塞，异步要求不阻塞

### 多线程适用场景

- CPU密集型操作
- 长期运行的任务
- 线程的创建与销毁开销较大
- 提供更底层的控制，操作线程、锁、信号量等
- 线程不易于传参及返回
- 线程的代码书写较繁琐

### 异步适用场景

- IO密集型操作
- 短暂的小任务
- 避免线程阻塞，提高系统响应能力



## 异步任务 Task

**包含了异步任务的各种状态的一个引用类型**：

​	正在运行、完成、结果、报错等

**对异步任务的抽象**：

- 开启异步后，当前线程不会阻塞
- 异步任务默认借助线程池在其他线程上运行
- 获取结果后回到之前的状态

**任务的结果**

- 返回值为Task的方法表示异步任务无返回值
- 返回值为Task<T>则表示有类型为T的返回值



## 异步方法 async Task

1. 将方法标志async后，可以在方法中使用await关键字，await关键字会等待异步任务的结束，并获得结果。

2. async + await 会将方法包装成状态机，await类似于检查点（MoveNext方法会被底层调用，从而切换状态）

3. **async void** 

   1. 适用场景：几乎限于 UI 事件处理程序（如按钮点击）。

      > [!WARNING]
      >
      > 即使在事件处理程序中，你也**必须**用 `try-catch` 块包裹所有代码，以防止异常导致应用程序崩溃。

   2. 不能被 await，方法不返回任何句柄。它是“一锤子买卖”。你启动了操作，但无法与之交互。

   3. 异常直接在触发时的同步上下文上抛出，通常会导致进程崩溃。

## 同步上下文

**同步上下文（SynchronizationContext）** 是一个 .NET 中的抽象类，它的核心职责是**在异步操作完成后，将代码的执行“调度”或“ marshals ”回原来的上下文**。

### 什么是同步上下文？

简单来说，同步上下文代表了代码执行所在的环境。这个环境有特定的线程亲和性（Thread Affinity）要求。最常见的两种环境是：

1. **UI 环境** (例如 WPF, WinForms, MAUI)：有一个主线程（UI线程），规则是**所有对UI控件的操作（如更新文本框、改变颜色）都必须在这个主线程上完成**。
2. **ASP.NET Core (及一般Web服务器) 环境**：规则是**没有特定线程亲和性**。任何线程池中的线程都可以处理请求，并且请求上下文在异步操作后不一定要回到原始线程。

`SynchronizationContext` 就是这个“环境规则”的对象表示。它提供了一个 `Post` 方法（异步）和一个 `Send` 方法（同步），用来将一段代码（委托）排队到它所代表的那个正确的上下文中执行。

### 为什么需要它？`async`/`await` 如何与它交互？

`async`/`await` 的关键特性是：在 `await` 之后的代码会尝试**回到原来的执行上下文**继续执行。这种行为提供了极大的便利性，让你在写异步代码时感觉像是在写同步代码。

**这个过程是如何实现的？**

1. 当你进入一个 `async` 方法时，它会捕获当前的 `SynchronizationContext`（如果存在的话），或者捕获当前的 `TaskScheduler`。
2. 当遇到 `await` 时，异步操作（例如一个 `Task`）被启动，当前线程被释放回调用方（不被阻塞）。
3. 当异步操作完成时，运行时希望继续执行 `await` 之后的代码。它会查看之前捕获的同步上下文：
   - **如果存在同步上下文**（例如在UI线程上）：它会使用该上下文的 `Post` 方法，将后续代码排队到**UI线程**上执行。这确保了你可以安全地操作UI控件。
   - **如果不存在同步上下文（为 `null`）**（例如在控制台程序或ASP.NET Core中）：后续代码会在**完成异步操作的那个线程池线程**上继续执行，没有强制回到特定线程的要求。



### 不同应用程序类型中的同步上下文

| 应用程序类型                          | 是否存在同步上下文？ | 行为描述                                                     |
| :------------------------------------ | :------------------- | :----------------------------------------------------------- |
| **UI 应用程序** (WPF, WinForms, etc.) | **是**               | 有一个专一的 `SynchronizationContext`（如 `DispatcherSynchronizationContext`）。`await` 后的代码会自动回到 UI 线程执行。这是为了线程安全地更新UI。 |
| **ASP.NET Web Forms / Legacy WCF**    | **是**               | 存在一个 `AspNetSynchronizationContext`，它旨在模拟旧的 ASP.NET 请求上下文（如 `HttpContext.Current`）在异步操作后的流动。 |
| **ASP.NET Core / 控制台应用程序**     | **通常为 `null`**    | 没有内置的、特定的同步上下文。`await` 后的代码会在线程池的任意可用线程上继续执行。**性能更高**，因为没有线程切换的开销。 |

### 重要实践：`ConfigureAwait(false)`

由于回到原始上下文有时是不必要甚至有害的（可能导致死锁或性能开销），.NET 提供了 `ConfigureAwait(false)` 方法来配置此行为。

```csharp
// 没有使用 ConfigureAwait(false)
var data = await httpClient.GetStringAsync("https://example.com");
// 在UI程序中，这行代码会回到UI线程
textBox.Text = data;

// 使用了 ConfigureAwait(false)
var data = await httpClient.GetStringAsync("https://example.com").ConfigureAwait(false);
// 这行代码不会尝试回到原始上下文，它会在线程池线程上运行。
// 因此，这里不能操作UI控件！
ProcessData(data); // 一个不涉及UI的纯计算或逻辑方法
```

**为什么要使用 `ConfigureAwait(false)`？**

1. **避免死锁**：在部分封闭式环境（如旧版ASP.NET）或错误的同步代码（例如 `.Result`）中，强制要求回到被阻塞的原始线程会导致死锁。`ConfigureAwait(false)` 避免了“回去”的需求，从而避免了死锁。
2. **提高性能**：避免调度回原始线程（尤其是UI线程）的开销，让后续代码在线程池上立即执行，可以提高吞吐量。对于不依赖特定上下文的代码（如库代码、数据处理代码），这应该成为标准写法。

**黄金法则**：

- 如果你在编写**库代码**（Class Library），**总是**使用 `ConfigureAwait(false)`，因为你不知道你的代码会在哪种应用程序（UI or Web）中被调用。
- 如果你在编写**应用程序级代码**（如按钮点击事件处理器），并且 `await` 之后的代码**需要操作UI**，那么**不要**使用 `ConfigureAwait(false)`。
- 如果你在编写**应用程序级代码**，并且 `await` 之后的代码**不操作UI**（只是数据处理、日志记录等），那么可以使用 `ConfigureAwait(false)` 来获得轻微的性能提升。

### 总结

- **同步上下文（SynchronizationContext）** 是代码执行环境的抽象，它定义了如何调度工作。
- 它的主要目的是在异步操作完成后**将执行流 marshals 回原始上下文**，这在UI程序中至关重要。
- `async`/`await` 默认会捕获并尝试回到原始同步上下文。
- 你可以使用 `ConfigureAwait(false)` 来显式告知运行时“不必回到原始上下文”，这对于提高库代码的性能和避免死锁至关重要。
- **ASP.NET Core 没有特殊的同步上下文**，这是其与旧版ASP.NET在异步行为上的一个关键区别，也使得它更高效、更简单。
