# ASP .NETCore Web API是什么？

​	ASP.NETCore Web API 是用于构建 HTTP API 服务的框架。它让应用程序可以通过 HTTP 协议向各种客户端（Web、移动、桌面、IoT设备等）提供数据和服务。

- MVC 前后端不分离，传输的是包含数据的HTML（UI）
- Web API 前后端分离，后端只写Web api接口，传输的是纯数据（通常是JSON）
- 主流方式是Web API 

| 特性       | ASP.NETCore MVC                                            | ASP.NETCore Web API                                          |
| :--------- | :--------------------------------------------------------- | :----------------------------------------------------------- |
| 主要目的   | 构建带有用户界面（网页） 的Web应用程序。                   | 构建HTTP API服务，为各种客户端（浏览器、移动App、其他服务）提供数据。 |
| 返回内容   | **视图（View） - 通常是HTML、CSS、JavaScript组成的网页。** | **数据（Data） - 通常是JSON或XML格式的结构化数据。**         |
| 通信协议   | 主要是HTTP/HTTPS，遵循请求-响应模式，服务于浏览器。        | 主要是HTTP/HTTPS，遵循RESTful原则或RPC风格，服务于任何能发送HTTP请求的客户端。 |
| 控制器基类 | 通常继承自 `Controller`（它本身继承了 `ControllerBase`）。 | 通常继承自 `ControllerBase`（更轻量，没有视图相关功能）。    |
| 项目模板   | 包含 Views 文件夹、CSS/JS文件，关注页面布局。              | 更简洁，主要关注 Controllers 和 Models，用于数据序列化。     |
| 内容协商   | 相对简单，主要返回HTML。                                   | 是核心功能，可以根据客户端请求头（`Accept`）返回JSON、XML等不同格式。 |
| 典型客户端 | Web浏览器。                                                | JavaScript前端框架（React, Angular, Vue）、移动应用、桌面应用、其他后端服务。 |

# 幂等是什么？

**幂等**（Idempotent）是一个数学和计算机科学中的概念，指**一个操作执行多次的结果，与执行一次的结果完全相同**。在 Web API 和分布式系统设计中，幂等性至关重要，因为它能保证即使在网络重试等情况下，系统状态也不会被意外改变。

### 1. 核心定义

- **数学定义**：对于函数 `f(x)`，若 `f(f(x)) = f(x)`，则 `f` 是幂等的。
- **API 中的含义**：客户端对同一个接口发起**多次相同的请求**，对服务器资源产生的**最终影响**与**只请求一次**相同。

注意：幂等性关注的是**对资源状态的影响**，而不是每次的响应内容必须一模一样。

### 2. HTTP 方法中的幂等性

在 REST API 中，不同的 HTTP 方法具有不同的幂等特性：

| HTTP 方法  | 是否幂等 | 说明                                                         |
| :--------- | :------- | :----------------------------------------------------------- |
| **GET**    | ✅ 是     | 获取资源，多次读取不会改变资源状态，是**安全**且幂等的。     |
| **HEAD**   | ✅ 是     | 与 GET 类似，只返回头部，也是安全的幂等方法。                |
| **PUT**    | ✅ 是     | 用于更新或创建资源。多次发送完全相同的 PUT 请求，最终资源状态与第一次请求后一致。例如连续两次 `PUT /users/1` 设置 name="Tom"，结果都是 name="Tom"。 |
| **DELETE** | ✅ 是     | 删除资源。第一次删除后资源已不存在，后续 DELETE 请求通常返回 404，但服务器状态（资源已删除）保持不变，因此是幂等的。 |
| **POST**   | ❌ 否     | 通常用于创建资源。每次 POST 都可能创建一个新资源（如提交订单），多次请求会产生多个订单，因此**不幂等**。 |
| **PATCH**  | ⚠️ 不一定 | 取决于实现方式。如果使用 JSON Patch 等标准，可能不幂等；但若设计为“将字段更新为指定值”，则可实现幂等。 |

### 3. 幂等 vs 安全

- **安全方法**（Safe Methods）：不会修改服务器状态的 HTTP 方法，如 `GET`、`HEAD`。安全方法一定是幂等的。
- **幂等方法**：允许修改服务器状态，但多次修改的结果与一次相同，如 `PUT`、`DELETE`。

### 4. 为什么幂等性很重要？

- **网络重试**：在不可靠的网络环境中，客户端常常因超时而重试。如果接口是幂等的，服务端可以安全地处理重复请求，不会造成数据错误（如重复扣款、重复下单）。
- **分布式系统**：在微服务间调用时，幂等性能简化容错逻辑，避免引入额外的去重机制。
- **REST 风格要求**：遵循 REST 原则的 API 应正确利用 HTTP 方法的幂等语义，使 API 行为可预测、更健壮。

### 5. 实际例子

- **非幂等操作**：用户提交订单 `POST /orders`，每次请求都会生成一个新订单。如果客户端因超时重试三次，可能产生三个相同内容的订单，导致库存混乱。
- **幂等操作**：支付接口设计中，通常要求传入一个**幂等键**（Idempotency Key）。例如，客户端发起支付请求时携带一个唯一令牌，服务端根据该令牌判断是否已处理过，若已处理则直接返回上次结果，从而保证多次请求只执行一次扣款。

### 6. 如何实现幂等？

对于非幂等的接口（如 `POST`），可以通过以下方式使其幂等：

- **客户端生成唯一请求 ID**（如 UUID），服务端记录该 ID，当收到重复请求时直接返回已处理的结果。
- **利用数据库唯一约束**：如订单号、业务流水号等，防止重复插入。
- **使用条件更新**（如 `If-Match` / `If-None-Match` 头）确保更新基于预期版本。

------

总之，幂等性是构建可靠、可重试 API 的基础，在 REST 设计、分布式事务、支付系统等领域广泛应用。理解并正确实现幂等，能避免大量因重试引起的脏数据问题。







# ASP .NET REST风格是什么？

REST 并非一项技术标准，而是一套架构约束和原则。它的核心思想是，把后端的功能也看作是“资源”，并通过 HTTP 协议的标准方式来操作这些资源。

[Route("[controller]")] REST风格

[Route("[controller]/[action]"] RPC风格

| 特性          | REST 风格                                           | 传统 RPC 风格 (如 SOAP, 旧式Web Service)               |
| :------------ | :-------------------------------------------------- | :----------------------------------------------------- |
| **核心概念**  | 以**资源**为中心 (如用户、订单)                     | 以**动作**为中心 (如函数、过程)                        |
| **URL 设计**  | 指向资源，如 `/api/users/123`                       | 描述动作，如 `/api/getUser?id=123`                     |
| **HTTP 方法** | 充分利用 **GET/POST/PUT/DELETE** 等表示对资源的操作 | 通常只使用 **GET/POST**，把动作藏在 URL 或请求体里     |
| **状态码**    | 使用 HTTP 状态码 (如 200, 201, 404) 表示结果        | 通常无论结果如何都返回 200，然后在响应体里自定义状态码 |

这种设计让 REST API 具有高度可读性、自描述性，并且充分利用了 HTTP 协议本身的特性。

但是实际业务中很难把所有的资源都分类清楚，基本不可能有纯REST开发。

有些公司也完全不restful，比如阿里，腾讯……







# Controller类 & ControllerBase类

###  1. ControllerBase 类

- **定义**：`ControllerBase` 是一个没有视图支持的基类，它提供了处理 HTTP 请求所需的最基础功能。
- **主要功能**：
  - HTTP 上下文访问（`Request`、`Response`、`HttpContext`）
  - 用户和会话（`User`、`ModelState`）
  - 请求数据和模型绑定
  - 返回状态码的辅助方法（`Ok`、`NotFound`、`BadRequest` 等）
  - 内容协商（返回 JSON/XML 等）
  - 授权和过滤器支持
- **适用场景**：**Web API 控制器**。如果你的控制器只需要返回数据（JSON/XML）而不需要返回视图（HTML），那么继承 `ControllerBase` 是最合适的选择。

### 2. Controller 类

- **定义**：`Controller` 继承自 `ControllerBase`，在基类的基础上增加了对**视图**的支持。
- **主要功能**：
  - 继承 `ControllerBase` 的所有功能
  - 视图相关方法：`View()`、`PartialView()`、`ViewComponent()` 等
  - 视图数据传递：`ViewData`、`ViewBag`、`TempData`
  - 支持返回视图结果（`ViewResult`）
- **适用场景**：**传统 MVC 控制器**。当你的控制器需要返回 HTML 页面（视图）时，应该继承 `Controller`。例如，在包含 Razor 视图的 Web 应用程序中。

### 3. 控制器类可以不继承 Controller 或 ControllerBase

**控制器类可以不继承 `Controller` 或 `ControllerBase`**，但需要满足框架发现控制器的条件。这种类通常被称为“POCO 控制器”（Plain Old CLR Object）。虽然技术上可行，但实际开发中几乎总是继承 `ControllerBase`（用于 API）或 `Controller`（用于 MVC）。

- **可以**：控制器类可以不继承任何基类，只需满足命名约定或 `[Controller]` 特性。
- **但通常不这样做**：因为会失去框架提供的大量便利功能，导致代码冗余且易错。
