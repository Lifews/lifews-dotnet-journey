## DTO

- **核心概念：** DTO 是一种**设计模式**。它是一个简单的容器对象，**专门用于在不同层（或子系统）之间传输数据**。
- **目的/解决的问题：**
  - **解耦：** 防止将内部领域模型（Entity / Domain Model）或数据库模型的细节直接暴露给外部（如 API 客户端、UI 层）。这提高了内部实现的灵活性和安全性。
  - **效率：** 优化网络传输。DTO 通常只包含客户端或接收方**真正需要**的字段，避免传输整个臃肿的领域对象（可能包含敏感信息、不必要的关系、循环引用等）。
  - **定制化视图：** 为不同的客户端或场景提供**定制化的数据视图**。例如，同一个 `User` 实体，在“用户列表”API 中可能只需要 `Id` 和 `Name`（`UserSummaryDto`），而在“用户详情”API 中则需要更多信息（`UserDetailDto`）。
  - **减少网络调用：** 有时一个 DTO 可以聚合来自多个领域对象或数据源的信息，减少客户端发起多次请求的需要。
  - **适配接口：** 使内部数据结构适应外部接口（如第三方 API 要求的数据格式）。
- **特点：**
  - **只有数据，没有行为：** DTO 通常只包含属性（getter/setter），不包含业务逻辑方法（或极少）。
  - **序列化友好：** 它们被设计成可以轻松序列化成 JSON、XML 或其他格式进行网络传输。
  - **扁平化：** 为了简化传输和处理，DTO 结构通常比内部领域模型更扁平，避免复杂的嵌套关系（除非必要）。
  - **可重复使用（但非必须）：** 可以在多个地方使用同一个 DTO，但更常见的做法是为不同的需求创建专门的 DTO。
- **例子：**
  - **API 请求/响应：** 客户端发送 `CreateUserRequestDto` 到服务器，服务器返回 `UserResponseDto`。
  - **服务间通信：** 微服务 A 调用微服务 B 时，使用 `OrderInfoDto` 传递订单数据。
  - **UI 数据绑定：** 后端提供给前端 UI 的数据模型通常是 DTO。

**简单来说：DTO 就像是数据的“信封”或“快递箱”。它不关心箱子里原来是什么样子（内部复杂的领域模型），它只负责把客户（外部调用者）需要的东西，用客户能理解的方式打包好送过去。**





## Mapster映射

- **核心概念：** Mapster 是一个 .NET 平台下**高性能、轻量级、功能丰富**的 **对象到对象映射 (Object-to-Object Mapping, OOM)** 库。
- **目的/解决的问题：** **自动化和简化** 在两种不同类型对象之间**复制数据**的过程，特别是当源对象和目标对象具有**相似但不完全相同**的结构时（最常见的场景就是把 **Entity/Domain Model** 映射成 **DTO**，或者反过来）。
- **为什么需要它？**
  - **避免样板代码：** 手动编写映射代码（如 `dto.PropertyA = entity.PropertyA; dto.PropertyB = entity.PropertyB; ...`）非常繁琐、冗长、容易出错且难以维护，尤其是在对象有很多属性或需要频繁映射时。
  - **提高开发效率：** Mapster 通过约定或简单配置自动完成大部分映射工作，极大减少了开发时间。
  - **性能：** Mapster 以其**极高的运行速度**著称（通常比手动映射慢不了多少，远快于一些其他流行的映射库如 AutoMapper），这对于性能敏感的应用很重要。
  - **灵活性：** 提供丰富的配置选项来处理复杂的映射场景：
    - 属性名称不一致（`Src.Name` -> `Dest.FullName`）。
    - 类型转换（`string` -> `int`, `DateTime` -> 特定格式的 `string`）。
    - 嵌套对象映射（`Src.Address` -> `Dest.ShippingAddress`）。
    - 集合映射（`List<SrcItem>` -> `List<DestItem>`）。
    - 条件映射（只映射满足特定条件的属性）。
    - 自定义映射逻辑（对某些属性进行特殊处理）。
    - 忽略某些属性。
