# 数据库事务

--20250806

​	数据库事务（Database Transaction）是数据库管理系统（DBMS）中的一个核心概念，它代表**一组数据库操作（如插入、更新、删除）组成的逻辑工作单元**。事务的目的是确保数据从一个一致状态安全地转换到另一个一致状态，即使在系统故障或并发操作时也能保持数据的完整性和可靠性。



## 核心特性：ACID

事务通过 **ACID 属性**来保证其可靠性：

1. **原子性（Atomicity）**
   - 事务中的所有操作要么**全部成功执行**，要么**全部失败回滚**（Rollback）。
   - **举例**：银行转账（A 转 100 元给 B）包含两步：
     - 从 A 账户扣款 100 元
     - 向 B 账户加款 100 元
       若第二步失败，第一步也会被撤销，避免资金损失。
2. **一致性（Consistency）**
   - 事务执行后，数据库必须保持**预定义的业务规则和约束**（如唯一键、外键、数据类型）。
   - **举例**：转账前后，A + B 的总金额应保持不变。
3. **隔离性（Isolation）**
   - 多个并发事务的执行互不干扰，每个事务感觉不到其他事务在同时运行。
   - **实现方式**：通过锁机制或 MVCC（多版本并发控制）实现不同隔离级别（如读已提交、可重复读）。
4. **持久性（Durability）**
   - 事务一旦提交（Commit），其结果**永久保存在数据库中**，即使系统崩溃也不会丢失。
   - **实现方式**：通过预写日志（Write-Ahead Logging, WAL）确保修改先记录到日志，再写入磁盘。





## 事务的生命周期

1. **开始事务**：显式（如 `BEGIN TRANSACTION`）或隐式（执行第一条 SQL 时自动开始）。
2. **执行操作**：执行增删改查（INSERT/UPDATE/DELETE/SELECT）。
3. **提交或回滚**：
   - **提交（COMMIT）**：确认所有操作，持久化到数据库。
   - **回滚（ROLLBACK）**：撤销所有操作，回到事务开始前的状态。



## 为什么需要事务？

1. **应对故障**
   - 系统崩溃、断电时，未完成的事务自动回滚，避免数据处于“半完成”状态（如扣款成功但未加款）。
2. **并发控制**
   - 防止多个用户同时修改同一数据导致冲突（如超卖、数据覆盖）。
3. **保证业务逻辑完整性**
   - 复杂操作（如订单创建需同时更新库存、支付状态）必须整体成功或失败。



## CAP事务

**CAP事务**并不是一个独立的事务类型，而是指在**分布式系统**中设计事务型应用时，必须遵循的**CAP定理约束**。

## 事务锁

**事务锁（Transaction Lock）** 是数据库管理系统（DBMS）中用于**实现事务隔离性和数据一致性**的核心机制。当事务访问数据时，锁会暂时限制其他事务对该数据的操作，防止并发冲突（如脏读、数据覆盖等）。锁的类型较多，此处先关注悲观锁和乐观锁。

- **共享锁（S锁）** 与 **排他锁（X锁）** 是基础锁类型，通过互斥规则保障数据安全。
- **行级锁** 和 **间隙锁** 支撑高并发与隔离性，需警惕死锁风险。
- 选择 **悲观锁**（先加锁）或 **乐观锁**（后校验）取决于业务。

| 类型       | 实现方式                           | 适用场景                   |
| :--------- | :--------------------------------- | :------------------------- |
| **悲观锁** | 默认并发会冲突，**先加锁再操作**   | 写密集、冲突率高（如支付） |
| **乐观锁** | 默认并发无冲突，**提交时校验版本** | 读密集、冲突率低（如评论） |
