## EXPLAIN性能分析

​	在 SQL 查询语句前加上 `EXPLAIN` 是一个关键的 **性能分析工具**，它用于显示数据库执行该查询的**执行计划**（Execution Plan），而非实际运行查询。其主要作用是帮助开发者理解数据库如何执行 SQL 语句，从而优化查询性能。

**核心作用**

1. **揭示查询的执行路径**
   显示数据库优化器选择的执行策略，例如：
   - 使用哪个索引（或是否全表扫描）
   - 多表连接的顺序和方式（如嵌套循环、哈希连接）
   - 是否使用临时表或文件排序（`Using temporary; Using filesort`）
2. **预估性能瓶颈**
   通过分析执行计划中的成本指标（如扫描行数、连接类型），定位慢查询的原因。
3. **验证索引效果**
   检查查询是否有效利用了索引，避免低效的全表扫描（`ALL` 类型）。



## 索引

​	索引是数据库中用于**加速数据检索**的数据结构，类似于书籍的目录。它通过建立特定字段的快速访问路径，避免全表扫描，显著提高查询效率。



### 一、索引的核心原理

```Mermaid
graph LR
A[SQL查询] --> B{是否命中索引？}
B -->|是| C[通过索引快速定位数据]
B -->|否| D[全表扫描]
C --> E[返回结果]
D --> E
```

1. **数据结构**：
   - 索引将列值转换为**有序结构**（如B+树）
   - 存储<键值, 数据位置>的映射关系
2. **工作流程**：
   - 查询时先在索引中查找键值
   - 通过指针直接访问对应数据行
   - 避免扫描整张表



### 二、索引类型详解

**1. 按数据结构分类**

| 类型         | 数据结构   | 特点                   | 适用场景                      |
| :----------- | :--------- | :--------------------- | :---------------------------- |
| **B+树索引** | 多叉平衡树 | 范围查询优秀，有序存储 | 主流数据库默认类型（MySQL等） |
| **哈希索引** | 哈希表     | 精确查询O(1)时间复杂度 | 等值查询（=）                 |
| **全文索引** | 倒排索引   | 支持文本关键词搜索     | 文章/内容搜索                 |
| **R树索引**  | 空间树结构 | 处理空间数据           | 地理坐标查询                  |



**2. 按逻辑功能分类**

| 类型         | 特点                               |
| :----------- | :--------------------------------- |
| **普通索引** | 最基本的索引类型                   |
| **唯一索引** | 确保列值唯一性                     |
| **主键索引** | 特殊的唯一索引，不允许NULL         |
| **组合索引** | 多列联合索引，遵循**最左前缀原则** |
| **覆盖索引** | 包含查询所需所有字段，避免回表查询 |
| **前缀索引** | 对文本字段前N个字符建立索引        |



### 三、索引关键特性

1. **最左前缀原则（Leftmost Prefixing）**

对于组合索引 `(col1, col2, col3)`：

```sql
-- ✅ 有效查询
SELECT * FROM table WHERE col1 = 'A';
SELECT * FROM table WHERE col1 = 'A' AND col2 = 'B';

-- ❌ 无效查询
SELECT * FROM table WHERE col2 = 'B'; -- 缺少最左列col1
SELECT * FROM table WHERE col3 = 'C'; -- 缺少前导列
```

**2. 索引覆盖（Covering Index）**

当索引包含查询所需的所有字段：

```sql
-- 假设索引为 (department, salary)
EXPLAIN SELECT department, salary FROM employees;
/* 
结果：
Extra: Using index 
*/
```

**3. 索引下推（Index Condition Pushdown, ICP）**

MySQL 5.6+ 优化：将WHERE条件过滤下沉到存储引擎层

```sql
-- 索引 (age, city)
SELECT * FROM users WHERE age > 20 AND city LIKE 'S%';
-- 存储引擎直接过滤age和city，减少回表次数
```



### 四、索引底层结构（B+树）

​	B+树是一种专为**磁盘存储系统优化**的平衡树数据结构，是现代关系型数据库（MySQL InnoDB、PostgreSQL等）索引的**标准实现**。其设计目标是**最小化磁盘I/O次数**，解决海量数据高效存取问题。

​	具体工作逻辑：	https://www.cs.usfca.edu/~galles/visualization/BPlusTree.html



### 五、索引优化实践

#### 1. 创建策略

| 场景          | 优化建议                           |
| :------------ | :--------------------------------- |
| 高频等值查询  | 单列索引                           |
| 范围查询+排序 | 组合索引（范围列在前，排序列在后） |
| 多条件AND查询 | 组合索引（高频条件列在前）         |
| 多条件OR查询  | 单列索引+`UNION`                   |
| 文本模糊查询  | 前缀索引 或 全文索引               |

#### 2. 索引失效场景

```sql
WHERE age + 1 = 30              -- × 表达式计算
WHERE name LIKE '%son'           -- × 前导通配符
WHERE YEAR(create_time) = 2023   -- × 函数包裹列
WHERE col1 = 1 OR col2 = 2       -- × OR非最左前缀（需改UNION）
```



### 六、索引的代价

1. **存储成本**：

   - 索引通常占表空间的10%-30%
   - 组合索引可能超过原数据大小

2. **维护成本**：

   | 操作   | 索引影响               |
   | :----- | :--------------------- |
   | INSERT | 需更新所有相关索引     |
   | UPDATE | 若修改索引列需重建索引 |
   | DELETE | 需清理索引条目         |

**平衡建议**：读写比大于10:1的表适合建索引



### 七、最佳实践总结

1. **创建原则**：

   - 频繁作为WHERE条件的列
   - ORDER BY/GROUP BY的列
   - JOIN连接列

2. **避免过度索引**：

   - 单表索引不超过5个
   - 定期使用`SHOW INDEX FROM table`分析索引效率

3. **监控工具**：

   ```sql
   -- MySQL查看索引使用情况
   SELECT * FROM sys.schema_index_statistics;
   
   -- PostgreSQL检测缺失索引
   SELECT * FROM pg_stat_all_indexes;
   ```

> 📌 **黄金法则**：索引不是越多越好，需要根据实际查询模式**精准设计**。合理的索引可使查询速度提升10-100倍，而错误的索引反而会拖垮数据库性能。



### 省流版

用自增主键索引的表，**在1600万条内B+树保持3层最优结构**，主键查询几乎无感知延迟（查询时间<0.x毫秒）。

**300万条** 开始监控，**1000万条** 制定分表方案，**3000万条** 分库分表！



### `type` 类型详解（性能降序）

​	在 MySQL 的 `EXPLAIN` 结果中，**`type` 列是最关键的指标之一**，它显示了 MySQL 如何查找数据行。以下是所有可能的 `type` 类型，按性能从最优到最差排序：

> [!WARNING]
>
> 在写代码的时候，多用explain查看是否有命中索引，千万不要没有命中索引！！！

| 类型                  | 名称       | 描述                                       | 示例场景                                                     |
| :-------------------- | :--------- | :----------------------------------------- | :----------------------------------------------------------- |
| **`system`**          | 系统表     | 表只有一行数据（系统表）                   | 从只有一行数据的系统表中查询                                 |
| **`const`**           | 常量查找   | 通过主键/唯一索引找到**唯一一行**          | `SELECT * FROM users WHERE id = 1`                           |
| **`eq_ref`**          | 唯一关联   | **多表 JOIN 时**，主键或唯一索引的等值匹配 | `SELECT * FROM users JOIN orders ON users.id = orders.user_id` |
| **`ref`**             | 索引查找   | 使用**非唯一索引**的等值查询，返回多行     | `SELECT * FROM users WHERE email = 'a@b.com'`                |
| **`fulltext`**        | 全文索引   | 使用全文索引检索                           | `SELECT * FROM articles WHERE MATCH(content) AGAINST('database')` |
| **`ref_or_null`**     | 索引或NULL | 类似 `ref`，但额外搜索包含 `NULL` 的行     | `SELECT * FROM users WHERE email = 'a@b.com' OR email IS NULL` |
| **`index_merge`**     | 索引合并   | **同时使用多个索引**，结果合并             | `SELECT * FROM users WHERE name = 'Alice' OR age = 30`       |
| **`unique_subquery`** | 唯一子查询 | 子查询中主键/唯一索引的 `IN()` 优化        | `SELECT * FROM users WHERE id IN (SELECT user_id FROM vip_users)` |
| **`index_subquery`**  | 索引子查询 | 类似唯一子查询，但使用非唯一索引           | `SELECT * FROM users WHERE dept_id IN (SELECT id FROM depts WHERE status=1)` |
| **`range`**           | 范围扫描   | **索引范围查找**（BETWEEN, IN, >, < 等）   | `SELECT * FROM orders WHERE amount > 100 AND amount < 500`   |
| **`index`**           | 全索引扫描 | 扫描整个索引树（**比 ALL 好，但需警惕**）  | `SELECT COUNT(*) FROM users`（覆盖索引时）                   |
| **`ALL`**             | 全表扫描   | **无索引可用，扫描所有行**（性能杀手）     | `SELECT * FROM users WHERE phone LIKE '%1234%'`              |



## 雪花ID

​	Snowflake ID（雪花ID）是 Twitter开发并开源的一种**分布式唯一ID生成算法**。它主要用于解决在分布式系统环境中，如何高效、可靠地生成全局唯一且大致有序的ID的问题。

```
| 0 	| 0000000 00000000 00000000 00000000 00000000 | 00000000 00 | 0000 00000000 |
| 1 bit |<------------------- 41 bits --------------->|<--10 bits-->|<---12 bits--->|
| 符号位 |<-------------------(时间戳) ---------------->|<--机器 ID -->|<----序列号---->|
```
